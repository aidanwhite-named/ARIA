# ADR 0002 — 검색 전략 프롬프트와 검색 실행 계약의 분리

- 상태: 채택 (2026-09-03)
- 적용 범위: `backend/app/search_prompt.py`, `search_contract.py`, `search_channels.py`,
  `search_plan.py`, `search_manifest.py`, `prompt_store.py`, `execution/runner.py`,
  `api/jobs.py`, `api/prompts.py`, `prompt/search_prompt.md`, 검색 화면·프롬프트 화면

## 문제

유사 문헌 검색의 프롬프트는 하나뿐이었고(`prompt/search_prompt.md`, 예약 프롬프트),
그 한 파일이 서로 다른 두 가지를 함께 담고 있었다.

1. **검색 전략** — 무엇을 중시하고, 어디까지 넓히고, 어떤 관점으로 후보를
   평가할 것인가. 사용자가 사건마다 바꾸고 싶어 하는 부분이다.
2. **실행 계약** — 청구항·명세서·미대응 구성의 데이터 경계와 placeholder,
   증거 등급, 분류 그룹의 정의, 후보 순서, 감사 블록 스키마.

둘이 한 파일에 있으면 두 가지가 동시에 성립할 수 없다.

- 사용자가 전략을 바꾸려면 계약을 지나가며 편집해야 한다. `{{CLAIM_TEXT}}` 를
  지우거나 `<CLAIM_TEXT>` 경계를 옮기면 청구항이 지시문과 같은 층위에 놓인다.
  검증으로 막고 있었지만, 애초에 사용자가 관리하지 않아도 되는 것이었다.
- 계약을 고치려면 사용자의 전략을 덮어써야 한다. 그리고 사용자가 파일을
  고쳐 두면 다음 배포에서 그 편집이 사라지거나 계약이 낡은 채 남는다.

실제로 갈라진 적이 있다. 분류 그룹 A/B 의 정의는 코드
(`search_manifest.GROUP_DEFINITIONS`)와 프롬프트 본문 양쪽에 있었고,
2026-08-25 실행에서 B 와 C 가 뒤집혀 인쇄됐다.

또 전략이 하나뿐이라 사건 종류별로 다른 검색 방식을 등록해 둘 수 없었다.

## 결정

프롬프트를 두 겹으로 나눈다. 사용자는 전략만 쓰고, 계약은 프로그램이 갖는다.

### 1. 프롬프트에 종류(kind)를 둔다

`prompt_store` 의 파일 메타데이터에 `kind: analysis | search` 를 둔다. 검색 전략
프롬프트는 여러 개를 등록·편집·선택할 수 있고, 배포본은 "지울 수 없는 기본값"
으로만 남는다. 종류가 없는 옛 파일은 예약 id 와 `similarity_search_v1` 선언으로
되돌려 읽는다.

두 목록은 섞이지 않는다. `/api/prompts?kind=analysis` 가 분석 실행의 선택지이고
`kind=search` 가 검색 실행의 선택지다. 조회도 종류를 걸어(`get_for_kind`) 한쪽
작업의 프롬프트가 다른 작업에 들어가는 경로를 만들지 않는다.

### 2. 데이터 구간은 프로그램이 조립한다

사용자 전략 본문 **뒤에** ARIA 가 데이터 구간을 붙인다(`search_contract`).

    [사용자 전략 본문]            ← 사용자가 자유롭게 바꾼다
    # ARIA 조립 데이터 구간        ← 아래는 전부 프로그램이 소유한다
      신뢰 경계 안내
      분류 그룹의 뜻 (코드의 정의에서 생성)
      후보 목록의 순서 (뒤따르는 공식 검증의 우선순위)
      ## 대상 청구항   <CLAIM_TEXT> … </CLAIM_TEXT>
      ## 검색 대상 구성 <SEARCH_FOCUS> … </SEARCH_FOCUS>   (있을 때만)
      ## 참고 자료: 명세서 <SPEC_TEXT> … </SPEC_TEXT>      (있을 때만)

사용자는 placeholder 도 경계도 관리하지 않는다. 전략 본문에 경계 표시를 적어도
붙이기 전에 중화되므로 데이터 구간을 위조할 수 없다.

청구항 단독 레인과 명세서 보조 레인의 격리는 그대로다. 명세서 구간은 보조
레인에서만 붙고, 기본 레인의 본문에는 명세서 이야기 자체가 없다.

### 3. 옛 프롬프트는 옛 경로로 돈다

본문에 `{{CLAIM_TEXT}}` 가 있으면 예전 계약 그대로 치환한다
(`template_mode: legacy_placeholders`). 이미 만들어 둔 프롬프트와 큐에 남아 있는
작업의 스냅샷이 계속 실행되어야 한다. 감사 기록에 어느 방식으로 조립했는지가
남으므로, 같은 청구항이라도 두 실행을 구별할 수 있다.

### 4. 채널 실행 정책은 프롬프트 문장이 정하지 않는다

`search_channels.resolve(values, channels=…)` 하나가 정한다. 입력은 작업 종류와
설정, 그리고 호출부가 명시한 채널 목록뿐이다. **프롬프트 본문이 들어가는 자리가
없다.** 프롬프트에 "검색하지 마라"라고 적혀 있어도 채널 정책은 바뀌지 않고,
"모든 DB 를 뒤져라"라고 적어도 꺼진 채널이 켜지지 않는다. 명시적 채널 목록은
범위를 좁히기만 하고 넓히지는 못한다.

채널은 web · literature · epo · kiwee 넷이며 서로 독립적으로 실행된다. 각 채널은
`SUCCEEDED / PARTIAL / FAILED / SKIPPED` 상태와 사유를 남기고, 한 채널의 실패나
출력 형식 오류가 다른 채널의 결과를 지우지 않는다. Kiwee 는 접속·인증이
구현되지 않았으므로 켜져 있어도 실행하지 않고 `SKIPPED / not_implemented` 로
기록한다 — 검색을 흉내 내지 않고 외부 요청도 보내지 않는다.

### 5. 검색 전에 정규화된 내부 계획을 만든다

`search_plan.build()` 가 청구항과 전략 본문에서 검색어·영문어·분류코드 후보·검색
대상 구성을 뽑아 고정 스키마로 남긴다. **모델을 부르지 않는다** — 계획은 관측
가능한 사실만 담아야 하고, 검증할 수 없는 것을 계획이라고 저장하면 "ARIA 가
관측한 사실"과 "모델이 해석한 내용"의 경계가 다시 무너진다.

이 스키마는 사용자 프롬프트에 노출되지 않고 거기에 의존하지도 않는다. 계획한
질의는 `manifest.plan` 에, 실제로 실행된 검색어는 `manifest.observed` 에 각각
남는다. 모델의 검색어를 한 건도 관측하지 못한 실행에서는 계획의 질의가 서지
채널의 대체 입력이 되며, 그 사실을 `literature.query_source` 에 적는다.

### 6. 감사와 보고서는 전략의 출력 형식에 의존하지 않는다

도구 호출·API 요청·응답 아티팩트·사용 검색어·URL·오류는 ARIA 가 직접 기록한다
(`search_manifest.observed`). 도구 이벤트만으로 얻을 수 없는 웹 후보의 필드는
**프로그램이 소유한 시스템 프롬프트**의 고정 스키마(`[ARIA_SEARCH_LOG_V1]`)로
받는다. 그 값은 "모델이 보고한 것" 칸으로만 들어가고 관측 사실과 같은 등급으로
합쳐지지 않는다. 사용자 보고서는 검증된 구조화 필드에서 ARIA 가 만든다.

## 결과

- 사용자는 전략만 쓴다. 전략을 어떻게 바꿔도 감사 기록과 표준 보고서는 나온다.
- 분류 그룹의 정의가 한 곳(`GROUP_DEFINITIONS`)에서만 나온다.
- 채널 상태가 매니페스트에 canonical 값으로 저장되고, 보고서는 같은 함수로
  같은 판정을 그린다.
- 매니페스트 버전이 12 로 올라갔다. 옛 기록에는 `prompt.name/kind/template_mode`,
  `channel_policy`, `channel_status`, `plan`, `kiwee` 가 없으며, 읽는 쪽은 없는
  것을 거짓이 아니라 **모르는 것**으로 다룬다. 옛 실행을 새 의미로 승격하지 않는다.

## 하지 않은 것

- 계획 단계에 LLM 턴을 추가하지 않았다. 필요해지면 같은 `SearchPlan` 계약 뒤에
  붙일 수 있지만, 그때도 계획의 출처(`generator`)를 기록에 남겨 관측과 해석을
  구분해야 한다.
- Provider 별 도구 허용 정책과 호출 상한은 그대로 두었다. 이 변경은 무엇을
  프롬프트가 정하고 무엇을 프로그램이 정하는가의 문제이지, 안전 한도를 조정하는
  문제가 아니다.
- Kiwee 의 실제 접속은 구현하지 않았다. 공급자 승인과 API 계약이 확정되기
  전까지 이 채널은 실행되지 않는다.
